# ADR-0018: Regelversions-Migration

**Status:** akzeptiert als technische Grundlage (setzt den Vorschlag aus ADR-0014 um). Wann und für wen migriert wird, ist eine Entscheidung der Spielserver-Schicht; hier ist nur der Mechanismus festgelegt.

**Kontext:** Es gibt jetzt mehrere Regelversionen (v1 bis v8). Ereignisse tragen ihre Regelversion; ein Replay unter anderen Regeln war bisher verboten (`RulesVersionMismatch`). Damit konnte keine bestehende Welt je auf neue Regeln wechseln. Ein stilles Neuberechnen der Geschichte unter neuen Regeln würde Figuren verfälschen.

**Entscheidungen**
1. **Der Wechsel ist ein aufgezeichnetes Ereignis** am Ende der Kette der Figur: `identity.rules_migrated`, aufgezeichnet unter der **neuen** Regelversion, Payload `{from, to, state_sha256, from_rules_sha256, to_rules_sha256}`. `state_sha256` = SHA-256 des kanonischen JSON der Teilzustände unmittelbar davor; die Regel-Fingerabdrücke sind SHA-256 über das kanonische JSON der Regeldaten (nicht der Dateibytes).
2. **Eine Stufe je Ereignis** in der Reihe der mitgelieferten Versionen (numerisch sortiert); mehrere Stufen = mehrere Ereignisse. Clients können das Ereignis nicht aufzeichnen (`CharacterService.record` lehnt den Typ ab); nur `migrate()` des Servers.
3. **Mehrversions-Replay** (`RulesChain`): Alte Ereignisse werden mit den alten Regeln abgeleitet; am Migrationsereignis werden Zustandshash, Regel-Fingerabdrücke, Stufe und Ereignis-Regelversion geprüft (Abweichung = `IntegrityError`: die Geschichte ist nicht mehr reproduzierbar, z. B. weil Regeldateien verändert wurden), der Zustand wird in die neue Version überführt, danach gilt die neue. Ohne `history_rules` verweigert der Dienst fremde Versionen wie bisher.
4. **Zustandsüberführung:** Alle Teilzustände bleiben erhalten; Engines, die die neue Version zusätzlich hat, starten mit ihrem Anfangszustand; strukturelle Änderungen kommen als Schrittfunktion `STATE_MIGRATIONS[(von, nach)]` (v7→v8 braucht keine). Entfernt die neue Version einen Teilzustand, wird die Migration **abgelehnt** (Fortschritt geht nie verloren), bevor etwas geschrieben wird.
5. **Eingefroren bis zur Migration:** Der Projector der aktuellen Version lehnt jede Validierung für einen Zustand anderer Version ab. Eine nicht migrierte Figur bleibt lesbar (Ansichten nutzen die Regeln ihrer Version, `rules_of`), kann aber an keiner Aktion teilnehmen, die Ereignisse erzeugt – Handel, Herstellung, Anstellung, Preishändler usw. scheitern vor jeder Bestandsänderung. Orders im Orderbuch können noch gestellt werden, ihre Ausführung scheitert an derselben Sperre.
6. **Welt-Upgrade** (`persistence.upgrade_world`): lädt dieselben Historien unter der höheren CEE-Regeldatei (Header von Regel-Hashes und Preisregeln werden angepasst), migriert die genannten Figuren (Standard: alle) und prüft die Weltkonsistenz; die Ausgangswelt bleibt unverändert, bei Fehlern entsteht keine neue Welt. Teil-Upgrades lassen eine Nachzüglermenge zurück, die einzeln migriert werden kann (`rules_migrate`). Gespeicherte gemischte Welten laden und fortsetzen sich unverändert (Persistenz, ADR-0014).
7. **Golden Vectors:** Weltszenario `rules_migration` (Start unter v7, `rules_upgrade` auf v8 mit zwei von drei Figuren, Fehlversuche, Nachzügler, `rules_migrate`); neue Operationen `rules_upgrade`, `rules_migrate`, Fehlerklasse `PersistenceError`. Bisherige Szenarien sind byte-identisch geblieben.

**Absicherung:** `tests/test_migration.py` (24 Tests: Ereignisinhalt, Replay von Grund auf, Sperre und Ansichten, Fälschungen mit gültiger Hash-Kette, Kette über mehrere Versionen mit neuen Engines, Schrittfunktion, Verlustschutz, Welt-Upgrade vollständig/teilweise/fehlgeschlagen, gemischte Welt speichern/laden/fortsetzen); Mutationstests (verbleibende Mutanten sind gleichwertig: mehrfach abgesicherte Prüfungen und Nachkontrollen).

**Offen / Grenzen**
- **Wann migriert wird** (alle zugleich nach einer Wartung, beim Login, nach einer Schonfrist), Ankündigung an Spieler und Rücknahme sind Betriebsentscheidungen. Es gibt keine Rückwärts-Migration (Downgrade) und keine Migration über mehrere Server gleichzeitig.
- Ein Migrationsereignis bindet an die **exakten** Regeldaten: Wer eine alte Regeldatei nachträglich ändert, macht alle Historien, die darüber migriert haben, unlesbar. Regeldateien einer veröffentlichten Version sind deshalb unveränderlich zu halten (Tests der Referenz pinnen sie).
- Gleichzeitige Migration mehrerer Figuren ist nicht atomar (je Figur ein Ereignis); `upgrade_world` arbeitet auf einer Kopie, damit ein Abbruch nichts zerstört.
- Welt-Regeln (Firmen, Markt, Produktion, Preise) haben noch keine eigene Versionsmigration; ihre Dateien sind per Hash an Snapshot und Vektoren gebunden, Änderungen sind bewusste neue Dateien/Formate.
- Die Standardregeln (`load_rules()`) bleiben v7 in der Referenz; der Wechsel des Standards auf v8 ist eine eigene Entscheidung.
